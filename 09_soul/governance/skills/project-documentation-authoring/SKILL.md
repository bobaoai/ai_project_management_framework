# 项目与技术文档写作

## 0. AI-facing Authoring Rules

<!-- embedded-resource:soul:bestpractice_ai_facing_writing:start -->
## 核心原则

### 原则一：先明确结果要求，再确定必要方法（结果确定性优先于过程确定性）

AI 开始写作前，应明确文稿要完成什么、服务什么读者，以及怎样判断内容已经正确、充分、可用。依据这些结果要求，确定需要交代的内容和采用的写作方法。

写作任务至少应明确四件事：

1. **目标**：文稿用于什么，读者需要从中获得什么理解、判断或执行能力。
2. **验收依据**：哪些要求决定文稿是否正确、充分并符合用途，如何核对这些要求。
3. **依据与方法**：使用哪些材料、知识和工具，哪些步骤或先后关系会影响结果。
4. **交付要求**：文稿需要达到什么深度，采用什么形式；已有明确的格式、路径或 schema 要求时，遵守相应要求。

凡步骤、顺序、工具或执行身份会影响正确性、授权边界或证据有效性的要求，应明确规定。例如，独立审核需要针对准确候选执行，审核结论需要与该候选对应。

其余方法由 AI 根据任务选择。步骤式指导、例子和经验，只要能帮助完成任务，就可以保留；避免强制执行与结果无关的过程，也避免只给目标而缺少必要方法。

### 原则二：支持 AI 自主判断，排斥 SOP

AI 具备推理能力。它的上下文容量有限。写入的内容应帮助它完成任务，减少无效的注意力消耗。

方法指导应提供建议和约束，保留 AI 选择执行路径的空间。避免将指导写成固定的标准操作流程（SOP）。

例如，市场分析可以按行业板块组织。如果当天的市场变化主要由一个宏观冲击驱动，AI 应能够选择全局分析。

已知陷阱应当写清楚。AI 可能无法仅凭当前上下文识别这些问题。真实的失败经验通常比泛泛的建议更有用。

保留一段内容前，检查两点：

1. 删除它是否会降低任务质量或成功率。
2. 它是在说明预期结果，还是在规定操作方法。

**优先保留预期结果的说明。操作方法只有在确实能提高任务成功率时才保留。**

---

### 原则三：先写清 AI-facing 文档的契约，再压缩表达

Skill 是 AI 执行任务时使用的契约文档。写作应先保证执行所需的信息完整，再优化篇幅和版面。

这条原则适用于主要供 AI 使用的稳定文档，包括顶层设计文档、路由文档、规则、公理和入口文档，如 `CLAUDE.md`、`AGENTS.md`。

#### 必须回答的六个问题

编写或评审任何 AI-facing 文档时，先确保文档能直接回答以下问题：

1. **这一层负责什么？** 说明这一层的用途。
2. **什么时候进入这一层？** 说明进入条件和触发信号。
3. **进入后先读什么？** 明确应优先遵循的权威依据（first authority），以及承载当前事实的来源（truth surface）。
4. **应该产出什么？** 说明输出形式，以及读者读完后应能理解、判断或完成什么（reader-end-state）。
5. **怎样与相邻层交接？** 说明上游期望什么、下游使用什么，以及失败时如何回退。
6. **哪些相邻概念容易混淆？** 说明它们的区别，以及什么时候应使用其他概念或入口。

**六个问题都写清后，再考虑如何缩短和整理文档。**

#### 契约完整优先于视觉简洁

文档应让 AI 在执行时找到完整的契约。压缩篇幅或调整版面时，必须保留关键边界。

避免以下四类写法：

- **合并不同的任务主线。** 不要为了减少路由表的行数，合并不同的重复性任务主线。实际产出形式不同的主线，应各占一行。
- **混淆层级。** 明确区分任务主线（task mainline）、Skill 层、写作网关层（writer gateway layer），以及确定性构建器与数据包层（deterministic builder / package layer）。名称相近的层尤其容易被误用。
- **只靠名称表达职责。** 名称可能有多种含义。例如，`manager` 可能指角色，也可能指模块。文档应直接说明对象负责什么、不负责什么。
- **先写摘要，后补契约。** 先写清详细契约，再写摘要。

#### 检查删去一段是否影响执行

写完一段后，检查：删去这段，AI 还能完成文档规定的读者目标任务吗？

- 能完成：这段是多余内容，应删除。
- 不能完成：这段属于契约，应保留。

这项检查与 FP4（删除不影响判断的信息）及 `bestpractice_prose_without_editorial_meta.md` 中的检查互为补充。它们删除无助于判断的句子，避免无效扩写；本项检查保留执行所需的契约，避免删减造成含义不清。AI-facing 文档应同时满足这两项要求。

### 原则四：固定不变量，保留实现选择

结果确定性优先于过程确定性。写作时还应区分：哪些结果要求必须保持一致，哪些实现选择应留给 AI。

约束所有细节会限制 AI 自主判断。缺少必要约束，会使系统反复改变同一对象的定义和做法，失去连贯性。

**必须固定的不变量**包括：

- 产物的规范路径与命名。
- 产物的身份字段，如 `report_date`、`asset_id`、`theme_id`。
- 上游依赖的身份与新鲜度契约。
- 产出此节点的唯一规范构建器（canonical builder）。不允许第二条产出路径。
- 与相邻 Skill、构建器和写作器的接口形式。

**应留给 AI 选择的内容**包括：

- 正文的具体写法。
- 判断路径与取舍。
- 中间过程的组织方式。
- 哪些证据需要重点展开，哪些只需简述。

写作时应明确区分这两类要求。固定不变量，使系统保持连贯，产物可以追踪，并能跨任务复用。保留实现选择，使 AI 能根据当前上下文作出合适判断。

如果文档只规定正文结构和写作步骤，却没有写清不变量，就会同时限制 AI 的判断空间，并允许产物偏离约定。

检查每条要求：

- 它属于不变量，还是实现细节？
- 如果属于实现细节，能否写成建议和失败信号，保留 AI 的选择空间？
- 不变量是否足以防止系统偏移，同时数量少到 AI 能记住和使用？

### 原则五：同时写清禁止事项和违规特征

仅写“不要做什么”，依赖 AI 主动注意并遵守禁令。AI 绕过禁令后，产物仍可能看似合格，禁令本身无法帮助它发现问题。

每条关键边界都应同时说明两件事：

- **禁止事项**：哪些行为或结果不被允许。
- **违规特征**：发生违规后，可以观察到什么。

例如，数据更新边界可以写成：

- **禁止事项**：数据更新完成前，不得编写投资经理（PM）报告。
- **违规特征**：已经产出报告，却没有确认 `daily_update_status.json` 中的 `blocking == false`。报告本身可能看不出问题，但上游数据的新鲜度要求尚未满足，需要通过后续复盘发现。

主题补充分析的边界可以写成：

- **禁止事项**：主题补充分析（theme overlay）不得替代任务的首要依据（first authority）。
- **违规特征**：报告的核心论述采用主题的一般结论，取代了对当前股票或当前市场的分析。读者据此判断主题，判断对象偏离了当前股票或市场。

描述违规特征时，尽量做到：

- 给出 AI 能在产出后检查的可观察特征。
- 指出缺少哪类证据或使用了哪个错误的依据来源（truth surface），不要只说“读起来不对”。
- 如果问题只能在后续环节发现，明确指出哪个环节能够发现。

这样，AI 在自主选择路径后，仍能检查自己是否越过边界。可观察的违规特征有助于发现仅凭禁令容易遗漏的偏差。

### 原则六：按陌生读者的理解顺序组织概念

执行者通常没有参与作者当时的讨论。写作顺序必须从读者已有的知识出发，使每个新概念只依赖读者已经知道、或前文已经说明的对象、任务与边界。

先明确读者的起点和目标：

- **读者起点**：进入时已经知道哪些对象、字段、工具和上游事实。
- **读者目标状态**：读完后能判断何时进入、应优先信任什么、需要产出什么、何时完成，以及何时停止或提交给有权处理的人。

引入新概念时，优先按以下顺序说明：

1. 当前对象、任务或可观察问题是什么。
2. 它与相邻对象、正常路径或读者已有认知有何关键差异。
3. 这项差异会改变什么执行、判断或交接。
4. 最后给出需要长期复用的正式名称。

Schema、协议对象或法律术语可以先定义，以保证精确。定义首次出现时，应同时说明其通俗含义、适用任务或操作影响，让读者能够理解这个名称的作用。

解释性段落应让陌生读者理解三件事：正在描述什么、为什么需要这样规定、会改变什么。纯字段表、枚举、代码块和引用块无需逐项回答这三个问题，但前后必须有足够的用途说明。

交付前统一检查是否存在缺陷。以下任一问题回答“是”，都必须修改或记录为审核发现（finding）：

- 是否在说明任务或对象前引入抽象术语，迫使读者暂存尚未理解的名称？
- 是否有解释性段落无法让读者理解正在说什么、为什么需要，以及会改变什么？
- 是否存在机械编号、教科书式口吻或不自然的概念堆叠？
- 是否在过短的篇幅内引入过多独立概念？
- 是否存在段落间的契约缺口或推理断层？
- 改写是否改变了权威来源中的数字、身份、权限、因果方向、不确定性、兼容性或停止条件？

最后一项检查保护原意。作者只能改善表达的可理解性。若更自然的措辞会改变权威来源的含义，应保留原意，或交由该内容的负责人决定；不得借润色重写契约。

## 1. Task

把具体项目的需求、设计依据和现有事实写成目标读者可以用于决定、协作、实现或验证的文档。可以从零起草，也可以修订已有文稿。作者首先恢复本次读者要完成的工作，再形成问题、方案、理由、具体行为和完成依据，保留项目决定与事实边界。

本 Skill 提供项目内容的专业写作方法。普通项目文档可直接进入；正式 Design 只有在属于具体项目的解决方案 T1 或技术 T2 时，才由 `the-design-authoring` 确定层级和所属规则后使用本方法。Primary Agent 在开始写作时按授权目标、用途和处理对象判断，始终维护同一份正文。Charter、T0 的新增与修订、通用治理设计及其他用途的 Design 继续原 DDM 路径；Skill 和 Reviewer 本体分别使用其原有编写入口。

## 2. Reader Gain

使用本 Skill 的 Agent 能判断哪些项目材料足以写作、关键问题属于事实还是决定、不同文档需要写到什么深度；能使业务读者理解方案，协作方接手工作，实现人员恢复已确定的技术行为，并据此形成可检查的完整文稿。

## 3. Entry and Exit

具体项目需要业务需求、提案、解决方案、技术详细设计，或这些交付中的操作与进展说明时进入。调用方提供目标、读者或读者需要作出的行动、当前阶段和可用材料；已有文稿修订还需当前全文、修改原因和需保留的含义。可从材料推断且风险有限的编辑选择由作者决定；会改变产品或业务结果的未定选择明确提出建议，交给有权决定的人。

缺少正文不阻止从零写作；缺少能够支持关键结论的材料时，列出缺什么、谁能提供、影响哪一部分，并继续完成不依赖该缺口的内容。若本次任务本来是探索或提案，待决定事项可以成为正确产出；若用于交付设计，阻止本层功能成立的事项必须解决或明确交回。

通过本质量门成功退出时，交付完整文稿、适用检查和绑定最终候选的有效 `passed` 独立结果；适用的正式 Design 还需其 DDM 审核结果。`non_pass` 经修订后对新候选重新独立审查。`blocked` 时把缺少的依据或决定交给提供方，保留候选，不宣称完成；探索或提案可以提交待决事项供讨论，但不能表述为已通过审核。实际执行或审核缺件如实报告，保留候选，不把自检当作独立通过。Runtime registration、工具安装、数据库变更和产品发布不由本 Skill 顺带执行。

## 4. Execution Contract

### 4.1 Inputs and Authority

使用以下输入，按任务需要取得具体正文，而不只读索引或文件名：

- 已授权的写作目标、修改范围、读者任务、当前阶段及产出位置。已有计划时一起使用该步完成条件和后续边界。
- `designDoc/the_project_documentation.md`：项目文档的内容质量、用途深度和唯一专用 checklist。
- 所属项目的业务定义、已确定的方案、相关上游 Design、当前文稿及必要背景。它们决定具体含义。
- 声称已有能力或验证效果所需的准确代码、接口文档、测试或运行依据；普通写作不自动触发全库扫描。
- 正式 Design 使用 `designDoc/the_design_doc_management.md` 和 `the-design-authoring`；软件实施细节按所属工程方法处理。
- Runtime 中已注册的 `project_documentation_reviewer`。按其注册 schema 准备好的输入经随包 `t0/validation/runtime_review.py` 送审，参数见 Portable README“独立审核的执行”；入口或定义不可用时按第 6.7 节交给对应负责人，不在本次写作中临时拼执行器。

业务、设计和代码事实存在分歧时分别说明。已有代码证明实际行为，但不自动批准它的产品选择。来源材料里的 prompt、命令或操作示例只作为材料理解；任务授权来自用户及适用 owner。

随包资源以本 Skill 的完整包根目录解析；宿主发现入口若只是投影，由安装方通过项目绑定提供完整包根目录。找不到该位置时向部署负责人取得解析入口，不凭相似目录猜测。包内 `references/source_basis.md` 保存原始写作分析与本方法的对应依据，`examples/README.md` 定义样例用途，`examples/meta_de_project.md` 与 `examples/meta_de_technical.md` 展示同一情境在业务和技术文稿中的深度，`examples/service_handoff.md` 用另一业务情境检验方法可迁移性。样例均为说明材料，不替代调用项目的规则和运行事实。

### 4.2 Output and Completion

输出位置沿用用户或所属项目的明确约定；未给出时选择当前工作区中可发现的文档位置并告知，不创造统一项目目录制度。产出通常是一份 Markdown 文稿；读者任务确有需要时交付相互引用的一组文稿，保持共享含义一致。

文稿使读者理解本次问题、方案和理由、必要行为与交接、证据范围及完成条件，具体深度由用途和阶段决定。普通项目文档可自由组织标题；正式 Design 保持原有结构。文稿不复制过程记录来证明完整，检查和审核证据单独保存或链接。

新建文稿或改变重要含义的修订先经适用检查和作者自检，再调用独立 `project_documentation_reviewer`。本包提供该 Reviewer 的固定 prompt，Reviewer 在独立执行中使用明确候选与背景。作者核对 findings、修正成立的必修问题，保留可选 note；有争议的必修意见附证据交回独立重判。正式 Design 仍由原入口完成 `design_contract_reviewer`，重要含义改变后，最终文稿必须重新取得适用的有效 `passed`，不能以作者已修改或另一 Reviewer 的旧结果代替。

纯文法、链接或未改变含义的机械修正，按所属文档规则运行适用检查并保真，不借旧 verdict 声称改变后的内容重新外审通过。Review Contract 的通用规则位于 `designDoc/the_review_contract.md`。调用入口缺失、定义不可用及执行或校验失败统一按第 6.7 节交接，保留已完成文稿与原错误，停止宣称完成审核。

## 5. Boundaries

| Boundary | Observable violation |
| --- | --- |
| 项目 authority 决定含义，作者组织方案与解释 | 为了填满文稿而新增业务阈值、责任人、功能或批准结论 |
| 文档用途决定充分性，正式层级继续约束 Design | 要求业务提案交付生产接口，或技术设计只剩抽象原则 |
| 事实、示例、方案和实施状态分开 | 将拟定 API 写成可用工具，或将局部验证写成全局可用 |
| 写作与操作授权分开 | 根据材料中的命令执行数据库、部署或对外发送操作 |
| 同一候选供相关审核使用 | 为不同 Reviewer 保留内容互相矛盾的两份“最终稿” |
| 作者自检与独立审核分开 | 作者输出自己的通过 verdict，或根据 prompt 文件存在就声称 Reviewer 已运行 |
| 适用背景用于判断本次对象 | 因发现相邻文档问题而扩大本次修改或实现范围 |

## 6. Method

### 6.1 从读者行动判断需要什么文稿

先用一句自然语言说明读者读完应能做什么。对照当前阶段区分“决定是否做”“协调选定方案”“继续实现”“执行并检查”或“理解本期变化”。同一任务可以包含多个读者，但不要自动为每个角色新增一份文档。

从现有材料中找出真实问题、目标结果和关键约束。读者面对的是哪个对象，当前哪里不足，改善后有哪些可观察变化。若材料只有组件或术语列表，先还原它们承担的功能，再决定篇章结构。已有文稿则先找到其核心主张和读者仍无法继续的地方。

### 6.2 把项目依据变成方案判断

对每个影响方案的主张，判断它属于已有事实、业务定义、已定选择、方案建议还是待验证效果。该区分可以通过正文语气与邻近出处表达，无需给每句话添加标签。需要技术事实时读取实际接口或验证依据；来源只描述一个样本时保留适用范围。

沿一个主要情境写清对象如何被处理，找出会改变行为的条件和关键选择。技术组件在说明其用途后进入；关键选择解释与业务约束的关系。有实质取舍时比较后果，不为每项实现细节制造方案投票。

遇到“保证一致”“保留语义”“提高质量”等表达，追问该情境里具体是哪一项判断发生变化。如果无法恢复对象、条件或结果，补依据或补设计，而不只把句子写长。

### 6.3 按实际用途展开细节

业务提案从真实场景和当前痛点推进到本期决定、可验证方案、谁交付什么、未证实事项与下一步证据；技术细节展开到支持该决定。该推进关系可以用连贯正文表达，无需把它固定成每篇相同的六个标题。解决方案沿功能与协作展开，让读者理解交接以后谁继续什么工作。

技术详细设计沿输入、关键处理和可观察结果展开。读者不易辨认交付物时，先给一个合格输入或输出的短例子，再解释字段含义和约束，说明违反条件会造成什么后果。解释关键数值时沿字段、含义、例子与计算口径说明它怎样影响使用判断；不能凭列名暗示含义。必要时使用协议表、伪代码、数据示例或流程图。核对一条记录和一次调用分别代表什么，图、正文和接口是否使用相同的条件与结果。对未改变本层行为的内部实现保持选择空间。

操作说明把动作与判断连接：对象在哪里、什么前提下可以执行、结果如何辨认、异常需要向谁交出哪些材料。进展说明给出自上次状态以来实际发生的可检查变化及影响，并说明“什么条件满足后可以开始什么”。条件已经解除时，更新接下来的实际动作，避免保留过时的等待状态；不要把平台能力介绍当成本期进展。

### 6.4 做好通用方法的项目适配

以本次需要的功能为单位，对照通用要求和项目事实。明确哪里复用已有定义或入口，哪里需要改变，哪里缺少能力。只有这项对应关系影响实现或决定时才使用映射表，关键理由仍写进正文。

消费调查材料时，分别还原预期规则、实际观察和差异对使用的影响。“部分”必须落实到已覆盖和未覆盖的对象；若旧调查已有确认或修订，让读者找到当前结论，同时保留原观察身份。未知含义写成有候选解释、能由专家回答的问题，说明回答改变哪条规则，确认后进入哪个已有说明。

不能因通用设计有一个逻辑操作，就假定目标数据库或应用具备同名 API。也不能为保持通用图形不变，把项目中不可满足的前提省略。出现能力缺口时说明它影响哪个承诺和后续负责人，给出当前依据允许的方案或待决问题。

### 6.5 沿具体情境走读并修订

假定读者没有本次聊天，按文稿继续一次主要工作。随后选择一个会改变处理的真实变体，例如输入不完整、已有记录修订、部分结果失败或条件改变。检查是否仍能恢复动作和结果，并核对相关文稿没有给出不同答案。

将发现的问题分到事实、业务决定、设计行为或表达。前三类回到其依据或负责人；表达类直接调整层次、补出因果、拆开规则和例外。修订先解决会改变读者行动的缺口，再处理可读性；无需把所有意见都变成新增段落。

### 6.6 Author Self-Check

<!-- embedded-resource:t0:skill_author_self_check:start -->
调用外部 Reviewer 前，author 必须直接消费本 Skill 声明的、由 subject authority 拥有的 canonical checklist，不能手抄第二份 checklist。每次调用只形成临时结果表：

| `check_id` | `exact evidence` | `local result` | `unresolved finding` |
| --- | --- | --- | --- |

每个 required `check_id` 恰好出现一次，并绑定当前 exact candidate 的证据。依据本次授权目标、适用计划步骤、完成条件与排除项判断当前必要性；历史 `prior_findings` 在当前候选上重新核对，不能继承旧 verdict。经核对成立且影响本步完成的必修问题列为 unresolved finding，先在本 Skill 内修订；note 不列入该栏，也不自动实施。对证据错误或越界的历史意见，在 exact evidence 中说明理由并交回独立 Reviewer 重判，不能自行改写原结论。只有没有已知未解决的必修问题时，才冻结候选并调用独立 Reviewer。

Author Self-Check 只防止作者把自己已经看见的缺口交给 Reviewer。它不产生 `passed`、approval、admission 或任何可替代独立审核的结果，也不创建持久化 record、Registry 或跨系统 schema。

作者直接消费下列 Project Documentation checklist。自检记录当前文稿证据，不复制另一份标准。正式 Design 的作者同时使用所属入口的检查，避免项目质量通过掩盖层级或 authority 缺陷。

<!-- embedded-resource:t0:project_documentation_review_checklist:start -->
1. `reader_task_and_stage`：读者任务、项目阶段和所需结果明确，文稿内容足以支持本次决定或工作；文档用途与 Design 层级没有混淆。
2. `problem_scope_and_outcome`：实际问题、影响、目标与范围有足够依据；拟建方案、现有行为和排除范围连贯，未加入未经授权的承诺。
3. `business_meaning_and_evidence`：影响决定的业务含义落实到可辨认的字段、条件、计算或问题，来源、示例和实际规则可区分；数量的单位与聚合口径支持业务判断。未知事项给出所缺定义或候选解释、可回答问题、提供方及当前影响。
4. `solution_reasoning_and_tradeoffs`：关键方案解释业务决定为何需要相应技术选择，存在实质选择时说明替代方案后果；机制理由与已验证效果分开，效果主张与证据范围相符，合理下层选择仍被保留。
5. `behavior_flow_and_handoff`：主要情境中的主体、条件、对象、动作及结果明确，必要交接与异常可恢复；实际涉及的图与正文一致。
6. `technical_and_cross_document_coherence`：技术含义、接口、粒度、单位、依赖和条件一致；输入输出足以让读者辨认合格结果，使用的例子、字段、规则与失败后果彼此相符，不能用大量字段掩盖返回对象粒度不明；成组文稿共享的范围、规则与状态一致。本次为纯业务文稿且无此类技术或跨文档内容时允许 `not_applicable`，须说明依据；业务规则本身仍由第 3 项检查。
7. `project_adaptation_and_actual_state`：通用方案与项目现有能力、复用、适配及缺项相符；调查明确预期与反例、部分范围及当前有效结论，进展说明有可检查变化、依赖及解除后的动作；未把拟定接口、有限验证或单次成功写成已有工具、全面完成或生产采用。
8. `completion_failure_and_next_action`：本阶段完成、部分结果、失败与待决定事项可判断，操作有必要的位置或对象、结果标准及异常交接依据，读者知道由谁继续什么；验证要求匹配所作承诺，不要求当前文稿交付下一层全部实现。
9. `prose_and_meaning_preservation`：前八项语义判断通过后，目标读者能按正文顺序建立理解；表达清楚且保持事实、职责、条件、因果与不确定性。语义未通过时使用 `not_run`。

### 6.7 独立审核与交付

将完整候选、读者任务、用途、阶段、范围及必要背景交给独立 `project_documentation_reviewer`。固定 prompt 与本次材料分开；样例仅在有助于判断时作为声明背景，不能代替候选的事实依据。

宿主按已注册的输入输出格式准备和检查材料，Runtime 按实际相容的入口执行。返回后确认技术执行、Runtime 共同格式校验，以及 Project Documentation 专用覆盖、适用条件、候选范围、finding 引用和结论一致性校验均成功，并取得准确输入与执行绑定，再解释结果。

失败按实际发生的阶段交接。先检查执行是否完成；执行未完成或执行状态未知时归执行问题。只有执行已完成而返回结果为空或格式无效时，才进入共同输出格式校验处理。定义本身有缺陷须有相应依据，不能仅凭一次运行失败就推断 prompt 或 schema 错误。

| 具体情况 | 唯一接收负责人及所需动作 |
| --- | --- |
| 环境没有提供独立调用入口 | 宿主环境维护者提供正确入口与配置 |
| 已有入口但目标 Module 尚未注册 | Runtime 注册负责人按 agent-runtime-registration 取得已审 source 和相应授权后处理 |
| 调用执行失败、执行状态未知或执行绑定失败 | Runtime 执行负责人检查原始执行与绑定事实 |
| 执行已完成，但结果为空或共同格式校验失败 | Runtime 共同校验负责人诊断输出和格式约定 |
| 专用覆盖、适用条件、候选范围或结论一致性校验缺失与失败 | Project Documentation 校验代码负责人补齐或修复专业校验 |
| 固定 prompt 或任务 schema 的定义有已确认缺陷 | 本套件 source 负责人按相应 authoring 方法修订定义 |

每种情况都保留原错误和已完成部分。作者不改变 Reviewer 所需能力，也不换用相似角色来制造通过。

交付时说明文稿在哪里、实际完成哪些检查和审核、仍影响使用的限制。若包含技术或运行承诺，保持其验证状态准确。样例走读和文稿审核不能被写成系统已实现或生产已部署。
