# 股票数据目录试点：让研究人员判断手头数据能否使用

> 说明性项目提案。下述范围和行为用于演示写法，实施与运行效果仍需项目采用及验证。

研究人员询问“有没有股票数据”时，需要同时知道有哪些股票、有哪些周期、实际覆盖到哪里、已经检查什么，以及从哪里读取。仅返回一张表的名称，会把理解数据与核实质量的工作继续交给使用者。

本试点为股票日线和 30 分钟线提供一个统一目录回答，并在数据提交后维护相关说明。团队据此判断首批目录是否足以支持选数，以及是否具备扩展到其他数据的条件。

## 本期提供什么

目录按可见数据集返回含义、粒度、来源、数量口径、更新约定、实际覆盖、质量结果和正式读取入口。它明确列出缺项，使使用者能区分“没有匹配数据”“没有权限”“尚未盘点”和“缺少判断规则”。

覆盖名单表示项目计划应覆盖的股票集合，由市场数据 owner 提供；它与实际已经取得数据的股票集合分别展示。仅在名单上而没有数据的股票单列为“应覆盖但尚无数据”，不计入实际有数据的股票数，也不与授权目录中没有匹配数据混为一类。股票数量按已经确认的股票身份去重。一只股票有两个周期或两个供应商来源时，不能因此算成多只股票。原始行数和按项目规则解析后的可读数据量分别说明，以免使用者将不同口径相加。

数据更新后，目录应能跟上对应依据。对同一条 bar 的修订即使没有改变最大时间，也可能影响质量和统计；维护因此依据准确修改和项目提供的提交信息，而不能只看时间边界。

## 功能怎样配合

数据 writer 按现有规则验证并提交。提交确认后，维护入口取得对应数据依据下的统计、覆盖和质量结果，再交目录组件关联和发布。检查任务将已确认提交与目录进度对照，发现漏项后补做未完成工作。

```mermaid
flowchart LR
    W["writer 确认数据提交"] --> M["维护入口准备统计、覆盖和质量"]
    M --> C["目录核对依据并发布"]
    C --> U["研究人员查询并选择数据"]
    H["检查提交与目录进度"] -->|发现缺项| M
```

查询读取已经整理好的目录，避免每次查询都扫描全量数据。代价是目录可能暂时落后；回答必须显示对应依据和未完成部分，使使用者据此决定等待维护还是使用已经具备依据的结果。

数据已提交但维护失败时，保留真实提交事实，补做维护。目录更新不能替代数据 writer 的验收，也不能授予业务读取权限。

## 采用前需要明确的条件

项目的数据 owner 提供股票身份、应覆盖名单、来源选择、正式读取方式和现有提交依据。项目授权负责人提供当前调用方允许查看的数据与目录披露规则；若这些规则尚未明确，受限查询验收保持待决，不能自行按目录缓存推定权限。具体更新频度来自已采用的采集约定；业务覆盖完整性和 bar 闭合状态需要对应日历及规则。

规则尚缺时，试点可以展示已有结构和观察到的边界，同时保留“未检查”或“规则未定义”。如果目标是证明某段区间完整，相关规则须先由 owner 确认，不能把最大时间等同于区间连续。

通用目录设计中的逻辑操作需要映射到本地实际接口。PostgreSQL 的存储事实与已有 writer 决定哪些版本依据可以取得；在没有历史重读能力的情况下，仅使用可证明的当前一致视图或已保存证据，不宣称支持任意过去版本读取。

## 怎样判断试点完成

团队在隔离环境中应观察到：有数据的股票与仅在覆盖名单中的股票被正确区分；供应商和周期重叠不重复增加股票数；同一条 bar 修订后目录识别相应变化；通知遗漏或维护失败能被发现并补做；权限受限的查询只得到允许披露的目录信息。

“数据成功提交”“目录已经对应”“质量已经检查”“适合当前业务使用”分别由各自证据支持。试点通过只说明已覆盖的情境和范围；扩大到其他资产、来源或生产调度需根据后续目标另作采用决定。
