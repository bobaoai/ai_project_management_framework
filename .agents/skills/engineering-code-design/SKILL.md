# 工程计划编写

## 0. AI-facing Authoring Rules

<!-- embedded-resource:soul:bestpractice_ai_facing_writing:start -->
## 核心原则

### 原则一：先明确结果要求，再确定必要方法（结果确定性优先于过程确定性）

AI 开始写作前，应明确文稿要完成什么、服务什么读者，以及怎样判断内容已经正确、充分、可用。依据这些结果要求，确定需要交代的内容和采用的写作方法。

写作任务至少应明确四件事：

1. **目标**：谁在什么情境下需要所设计的能力或任务产物，以及应获得什么实际结果。
2. **验收依据**：哪些要求决定文稿是否正确、充分并符合用途，如何核对这些要求。
3. **依据与方法**：使用哪些材料、知识和工具，哪些步骤或先后关系会影响结果。
4. **交付要求**：文稿需要达到什么深度，采用什么形式；已有明确的格式、路径或 schema 要求时，遵守相应要求。

凡步骤、顺序、工具或执行身份会影响正确性、授权边界或证据有效性的要求，应明确规定。例如，独立审核需要针对准确候选执行，审核结论需要与该候选对应。

其余方法由 AI 根据任务选择。步骤式指导、例子和经验，只要能帮助完成任务，就可以保留；避免强制执行与结果无关的过程，也避免只给目标而缺少必要方法。

#### Intended Outcomes：统一表达预期结果

Design 和 Skill 用一个 `Intended Outcomes` 章节集中表达主要结果要求。每项主要能力应有对应的实质结果，并说明接收者用途和决定结果能否使用的必要质量。不能只列产物名称，或用“完整、可靠、可实施”等词代替具体要求。目的、范围和适用条件以解释结果所需的深度保留。

作者先从授权目标和主要能力确定结果，再逐章反向核对全部正文；对象定义、职责边界和共同约束等位置也可能含有重要结果要求。重要结果或必要质量若只在后文出现，应补入结果章节；局部字段、操作步骤和检查命令仍放在所属位置。多项能力可以共享一个结果，一项能力也可以产生多个结果。不设固定条数、篇幅或逐项同名的要求，不为凑全内容增加未经授权的能力。

同一结果可以在不同章节出现：结果章节定义要达到什么，方法说明怎样达到，完成与验证说明凭什么确认。各处履行不同职责，不算重复定义；重复整项要求时才合并。修订先保留有效含义，再组织表达，不只更换标题或拼接旧段落。

Design 描述所设计系统或能力的功能与作用。Skill 描述执行任务的交付、接收者用途和必要质量。专业知识文稿需要说明其提供哪些专业认识，以及这些认识支持何种判断；是否使用固定章节沿其所属文稿规则确定。

“读者能找到入口、理解职责”等要求用于作者和 Reviewer 的冷读检查，正文直接把入口和职责讲清楚。教学、培训等任务以读者能力变化为实际产出时，可以将具体可验证的能力写成预期结果。

结果章节说明要做成什么，后续对应章节说明如何实现。Skill 在 `Method` 中写判断方法和操作过程，在 `Inputs and Completion` 的三个子节中分别明确输入、输出规格和完成条件；Design 按所属层级在功能、流程、架构和接口章节中明确必要工作方式。影响正确性、权限或证据有效性的指定方法必须写清楚，不能仅凭执行过方法就判定结果已经成立。

结果确定性要求目标和判断依据明确，并给执行者保留方法选择空间。信息不足时准确交付未知及其影响也可以符合结果要求，不承诺每次得到同一个结论或必须填满所有字段。当前进度、阶段安排和运行记录保留在对应项目或交付记录中。

### 原则二：支持 AI 自主判断，排斥 SOP

AI 具备推理能力。它的上下文容量有限。写入的内容应帮助它完成任务，减少无效的注意力消耗。

方法指导应提供建议和约束，保留 AI 选择执行路径的空间。避免将指导写成固定的标准操作流程（SOP）。

例如，市场分析可以按行业板块组织。如果当天的市场变化主要由一个宏观冲击驱动，AI 应能够选择全局分析。

已知陷阱应当写清楚。AI 可能无法仅凭当前上下文识别这些问题。真实的失败经验通常比泛泛的建议更有用。

保留一段内容前，检查两点：

1. 删除它是否会降低任务质量或成功率。
2. 它是在说明预期结果，还是在规定操作方法。

**优先保留预期结果的说明。操作方法只有在确实能提高任务成功率时才保留。**

### 原则三：先写清 AI-facing 文档的契约，再压缩表达

Skill 是 AI 执行任务时使用的契约文档。写作应先保证执行所需的信息完整，再优化篇幅和版面。

这条原则适用于主要供 AI 使用的稳定文档，包括顶层设计文档、路由文档、规则、公理和入口文档，如 `CLAUDE.md`、`AGENTS.md`。

#### 必须回答的六个问题

编写或评审任何 AI-facing 文档时，先确保文档能直接回答以下问题：

1. **这一层负责什么？** 说明这一层的用途。
2. **什么时候进入这一层？** 说明进入条件和触发信号。
3. **进入后先读什么？** 明确应优先遵循的权威依据（first authority），以及承载当前事实的来源（truth surface）。
4. **应该产出什么？** 说明预期的功能、产物或状态变化、接收者用途和必要质量；输出形式按实际交付需要确定。
5. **怎样与相邻层交接？** 说明上游期望什么、下游使用什么，以及失败时如何回退。
6. **哪些相邻概念容易混淆？** 说明它们的区别，以及什么时候应使用其他概念或入口。

**六个问题都写清后，再考虑如何缩短和整理文档。**

#### 契约完整优先于视觉简洁

文档应让 AI 在执行时找到完整的契约。压缩篇幅或调整版面时，必须保留关键边界。

避免以下四类写法：

- **合并不同的任务主线。** 不要为了减少路由表的行数，合并不同的重复性任务主线。实际产出形式不同的主线，应各占一行。
- **混淆层级。** 明确区分任务主线（task mainline）、Skill 层、写作网关层（writer gateway layer），以及确定性构建器与数据包层（deterministic builder / package layer）。名称相近的层尤其容易被误用。
- **只靠名称表达职责。** 名称可能有多种含义。例如，`manager` 可能指角色，也可能指模块。文档应直接说明对象负责什么、不负责什么。
- **先写摘要，后补契约。** 先写清详细契约，再写摘要。

#### 检查删去一段是否影响执行

写完一段后，检查：删去这段，AI 还能完成文档规定的读者目标任务吗？

- 能完成：这段是多余内容，应删除。
- 不能完成：这段属于契约，应保留。

这项检查与 FP4（删除不影响判断的信息）及 `bestpractice_prose_without_editorial_meta.md` 中的检查互为补充。它们删除无助于判断的句子，避免无效扩写；本项检查保留执行所需的契约，避免删减造成含义不清。AI-facing 文档应同时满足这两项要求。

### 原则四：固定不变量，保留实现选择

结果确定性优先于过程确定性。写作时还应区分：哪些结果要求必须保持一致，哪些实现选择应留给 AI。

约束所有细节会限制 AI 自主判断。缺少必要约束，会使系统反复改变同一对象的定义和做法，失去连贯性。

**必须固定的不变量**包括：

- 产物的规范路径与命名。
- 产物的身份字段，如 `report_date`、`asset_id`、`theme_id`。
- 上游依赖的身份与新鲜度契约。
- 产出此节点的唯一规范构建器（canonical builder）。不允许第二条产出路径。
- 与相邻 Skill、构建器和写作器的接口形式。

**应留给 AI 选择的内容**包括：

- 正文的具体写法。
- 判断路径与取舍。
- 中间过程的组织方式。
- 哪些证据需要重点展开，哪些只需简述。

写作时应明确区分这两类要求。固定不变量，使系统保持连贯，产物可以追踪，并能跨任务复用。保留实现选择，使 AI 能根据当前上下文作出合适判断。

如果文档只规定正文结构和写作步骤，却没有写清不变量，就会同时限制 AI 的判断空间，并允许产物偏离约定。

检查每条要求：

- 它属于不变量，还是实现细节？
- 如果属于实现细节，能否写成建议和失败信号，保留 AI 的选择空间？
- 不变量是否足以防止系统偏移，同时数量少到 AI 能记住和使用？

### 原则五：同时写清禁止事项和违规特征

仅写“不要做什么”，依赖 AI 主动注意并遵守禁令。AI 绕过禁令后，产物仍可能看似合格，禁令本身无法帮助它发现问题。

每条关键边界都应同时说明两件事：

- **禁止事项**：哪些行为或结果不被允许。
- **违规特征**：发生违规后，可以观察到什么。

例如，数据更新边界可以写成：

- **禁止事项**：数据更新完成前，不得编写投资经理（PM）报告。
- **违规特征**：已经产出报告，却没有确认 `daily_update_status.json` 中的 `blocking == false`。报告本身可能看不出问题，但上游数据的新鲜度要求尚未满足，需要通过后续复盘发现。

主题补充分析的边界可以写成：

- **禁止事项**：主题补充分析（theme overlay）不得替代任务的首要依据（first authority）。
- **违规特征**：报告的核心论述采用主题的一般结论，取代了对当前股票或当前市场的分析。读者据此判断主题，判断对象偏离了当前股票或市场。

描述违规特征时，尽量做到：

- 给出 AI 能在产出后检查的可观察特征。
- 指出缺少哪类证据或使用了哪个错误的依据来源（truth surface），不要只说“读起来不对”。
- 如果问题只能在后续环节发现，明确指出哪个环节能够发现。

这样，AI 在自主选择路径后，仍能检查自己是否越过边界。可观察的违规特征有助于发现仅凭禁令容易遗漏的偏差。

### 原则六：按陌生读者的理解顺序组织概念

执行者通常没有参与作者当时的讨论。写作顺序必须从读者已有的知识出发，使每个新概念只依赖读者已经知道、或前文已经说明的对象、任务与边界。

先明确读者的起点和目标：

- **读者起点**：进入时已经知道哪些对象、字段、工具和上游事实。
- **读者目标状态**：读完后能判断何时进入、应优先信任什么、需要产出什么、何时完成，以及何时停止或提交给有权处理的人。

引入新概念时，优先按以下顺序说明：

1. 当前对象、任务或可观察问题是什么。
2. 它与相邻对象、正常路径或读者已有认知有何关键差异。
3. 这项差异会改变什么执行、判断或交接。
4. 最后给出需要长期复用的正式名称。

Schema、协议对象或法律术语可以先定义，以保证精确。定义首次出现时，应同时说明其通俗含义、适用任务或操作影响，让读者能够理解这个名称的作用。

解释性段落应让陌生读者理解三件事：正在描述什么、为什么需要这样规定、会改变什么。纯字段表、枚举、代码块和引用块无需逐项回答这三个问题，但前后必须有足够的用途说明。

交付前统一检查是否存在缺陷。以下任一问题回答“是”，都必须修改或记录为审核发现（finding）：

- 是否在说明任务或对象前引入抽象术语，迫使读者暂存尚未理解的名称？
- 是否有解释性段落无法让读者理解正在说什么、为什么需要，以及会改变什么？
- 是否存在机械编号、教科书式口吻或不自然的概念堆叠？
- 是否在过短的篇幅内引入过多独立概念？
- 是否存在段落间的契约缺口或推理断层？
- 改写是否改变了权威来源中的数字、身份、权限、因果方向、不确定性、兼容性或停止条件？

最后一项检查保护原意。作者只能改善表达的可理解性。若更自然的措辞会改变权威来源的含义，应保留原意，或交由该内容的负责人决定；不得借润色重写契约。

## 1. Task Summary

修改交付代码、schema、migration 或测试前，使用本 Skill 编写或修订工程计划，名称为 `CodeDesignBasis` 或 plan doc。计划说明目标、方案、范围和验证安排，经过独立外审后交给实现负责人。

计划可以是一份 Markdown，也可以是现有工作文档中的明确章节。已有适用计划时先核对能否复用，不重复写第二份 Plan。

## 2. Intended Outcomes

交付一份实现负责人可据以实施、Reviewer 可据以判断的工程计划。计划应达到以下结果。

1. **目标差异和本批范围明确。** 所属设计与当前代码各有准确依据，计划说明当前行为与目标行为的差别、修改理由、纳入内容、排除项及后续边界。必要产品决定已经明确，未决定事项不会被现有代码或作者假设填补。
2. **主要改法足够具体。** 方案定位正确的模块和调用或数据路径，明确行为、接口、输入输出及副作用的变化。必要取舍说明依据、理由与代价，新增抽象有独立职责。真实调用方、兼容、依赖和失败影响得到处理，接手者无需猜测修改位置或另定关键方案。实施先后由实际依赖决定；需要分批时，各批有可独立验证的结果和完成条件，不把不影响本批的未来整合作为前置。
3. **字段和参数能够被正确消费。** 实际新增或修改的字段、枚举和参数有唯一用途、明确含义、产生方、后续动作及验证安排。共同取值沿用准确来源，不把不同事实混成综合状态，也不设计无人消费的字段。
4. **验证安排能证明目标行为。** 每项适用检查说明能发现什么错误；必要负例、兼容和恢复有覆盖。确定性检查与真实接口验证的用途、运行条件和未验证范围可区分，计划不要求未来代码已经通过，也不用无关集成增加前置。
5. **实施交接有准确依据。** 完整候选、自检、检查和独立计划审核相互对应。计划复用有覆盖本次工作的理由，必要实施授权明确。缺少设计、权限、材料或审核条件时，草稿、具体影响和负责人一并交出；计划通过不冒充代码或环境操作已经完成。

## 3. Boundaries

Software Delivery 规定工程计划和审核要求。所属 Design 决定预期行为、职责与接口；当前代码和测试提供实现事实。本 Skill 负责实现方案，不从旧代码或 Reviewer 偏好反推产品要求。

Charter 确定项目范围和人类决定权；T0 确定共同概念与职责；T1 确定领域协作；T2 确定有界能力的行为及必要接口。具体工程选择由计划决定。缺少上层决定时交给 Design 负责人，使用 the-design-authoring 补齐；不要求上层替工程方案决定全部内部机制。

按 `designDoc/the_system_change_governance.md` 第 4.1 节判断统一规划入口。用户明确要求统一规划，或者未指定起点且修改需要跨层统筹范围、职责和依赖时，交由 Primary Agent 使用 `the-system-change` 形成统一计划。用户已经指定代码起点时，直接形成工程计划，不额外强加 SystemChangePlan，仍须完成本 Skill 规定的计划和实施前外审。工程内部依赖和实施顺序在本计划中说明。已有统一计划时继承相关步骤、完成条件、排除项和后续边界。

| 分工 | 可观察的越界 |
| --- | --- |
| 实施前形成计划并独立审核 | 先修改交付代码，再根据 diff 补写所谓实施前计划。 |
| 所属 Design 决定目标 | 为适应当前代码或通过审核，新增产品行为或改变同级职责。 |
| 方案进入正确的现有实现 | 为少改几行而增加平行 wrapper、Registry 或隐藏入口。 |
| 按本次结果选择验证 | 将未涉及的数据库、网络、模型或未来集成作为当前前置。 |
| 作者自检与独立外审分开 | 作者自行写 passed，或把用户确认当成独立审核。 |
| 计划交付与实现、发布分开 | 计划通过后便声称代码已经完成，或在本 Skill 中直接实施、发布、部署。 |
| 字段与取值服务实际处理 | 字段、枚举或参数没有对应的代码分支、Agent 动作或验证。 |

## 4. Inputs and Completion

### 4.1 Inputs

进入时取得以下材料，并按用途判断缺口：

- 授权目标、明确范围、验收要求和已有计划（如有）。请求已指定交付位置时一并取得。
- `designDoc/the_software_delivery.md`：第 4.1 节说明工作入口，第 4.2 节定义工程计划内容，第 5、6 章规定审核和完成。
- 所属 Design、当前代码、实际入口、接口和判断方案所需的测试。只读取真实相关材料，区分设计要求与当前事实。
- 实际涉及的依赖、兼容、数据、环境影响和恢复要求。
- engineering-change-review 所用的独立工程审核入口，以及需要重新判断的历史 finding。

Code Design 或 implementation 只有在实际触及对应 machine-facing meaning 时才增加下列 authority input：
新增或修改 time-bearing field、clock、calendar、freshness 或 time comparison 时，先读取
`designDoc/the_timestamp_semantic.md`；新增或修改 schema 或 machine boundary 中的 Identifier、Reference、
version、content hash、pointer 或 locator 时，先读取
`designDoc/the_identifier_and_reference_semantics.md`。只是在局部变量、普通 prose、路径或未改变的既有
字段中出现 date、ID、ref 等词，不构成适用条件。未触及这些语义时不加载对应 T0，也不增加字段、占位
章节或空引用；触及时只绑定适用规则，不复制 peer contract，也不由 Code Design 或 Reviewer 重新定义。

层级和设计文稿规则使用 `designDoc/the_design_doc_management.md`。已有计划只有在内容未变、原外审仍适用，且目标、范围、接口、依赖和验证要求覆盖本次修改时，才可复用。说明复用依据，不把范围明确等同于可以省略计划。缺少产品或架构决定时，将具体问题交给有权决定的负责人。

### 4.2 Output

向本次请求方和实现负责人交付完整工程计划、作者自检、适用代码检查、独立计划审核结果及交付说明。计划包含 Software Delivery 第 4.2 节规定的五类内容，质量要求沿用本 Skill 第 2 章。

请求指定位置时使用该位置；未指定时，作者在项目适用的文稿位置保存候选并报告准确入口。修订保留原计划与审核证据，使用完整新候选承载变化。配套材料各给出可定位入口，交付说明列出实际完成程度、实施授权、未完成事项及其负责人。

计划先给最小有用的 Flowmap，再写必要接口和实现说明。涉及 schema 字段、枚举、状态或参数时，使用第 5.2 节的字段表。只有真实需要机器区分的失败才定义或引用错误合同，不为每个图节点创造 interface ID、error code、状态或 Registry。

### 4.3 Completion Contract

当前完整计划完成自检及适用检查，取得有效独立工程计划 passed，并且实施授权已经覆盖后，才交给实现负责人开始修改。已有明确授权不重复申请。复用计划须满足第 4.1 节条件；计划改变后重新检查和独立外审。

有效 non_pass 的成立缺陷交回计划作者。必要 Design、权限或其他输入缺失时，保留草稿，说明影响并交给其负责人。审核入口或执行条件不可用时，交给执行环境负责人。执行或输出校验失败没有有效 verdict，不能把草稿、用户确认或代码完成后的审核称为实施前外审通过。

交接时区分完整计划已准备、独立审核已通过和实施授权已具备。实现后的修复若仍符合原计划，按该计划处理；目标、接口、职责、关键依赖或验证方案需要改变时，按 Software Delivery 重新规划和审核。本 Skill 不接管后续实现、发布或部署，整体任务仍由 Primary Agent 负责。

## 5. Method

### 5.1 从当前行为推导工程方案

先还原行为，再确定改法，最后推导验证。每项判断使用第 4.1 节的依据，具体方案服从已定设计和本次授权结果。

1. **沿实际调用路径找差异。** 阅读所属 Design、入口、模块、数据读写、调用方和现有测试。说明当前行为与目标行为差在哪里，追到承载行为的代码位置，不只凭文件名或测试名称选修改点。区分已有实现、已验证行为和尚待实现的要求。依据清楚的差异进入工程计划；只有缺少设计决定，或新证据表明既有要求无法同时成立时，才将具体问题交回 Design，不能用当前代码补定产品要求。
2. **确定改法与影响范围。** 判断现有模块和接口能否承载变化，写清逻辑、输入输出和副作用，以及受影响的真实调用方、数据和兼容行为。新增抽象须说明原职责为何不足；有实质取舍时说明理由和代价。涉及写入或外部调用时，明确失败位置和已经发生的影响。改变上层含义的决定仍交回 Design，不为少改代码增加平行入口。
3. **从目标行为倒推验证。** 用具体输入走读拟议路径，核对结果、副作用、失败与兼容行为，再选择能证明要求的测试。每项验证说明能发现什么错误，不能仅靠字段存在或调用成功支持更强结论。涉及数据或上线影响时安排恢复验证；未涉及的数据库、网络或模型不成为前置。此时交付验证安排，不要求未来代码已经通过，也不把走读算作实际执行证据。

测试按证据类型标记。新增或行为被修改的测试各使用且只使用 `deterministic` 或 `real_run` 中一个 marker。`deterministic` 检查无需启动 Provider、Runtime 执行或数据库连接即可判断的规则，例如参数互斥、schema、hash 和状态判断。经过 Provider、Runtime 执行或数据库的测试必须为 `real_run`，走所验收路径的真实入口和依赖，不能使用替身，并设置显式环境门。未执行时报告 skipped 和未验证。

已有 `fake_run` 替身测试保留原标记，在其行为下次被修改时改为 `real_run`。计划写明各 repo 注册 marker 的位置、分开运行的命令和分别报告结果的方法。替身通过和此前的真实运行都不能证明新链路已成立。

例如，要保证必需测试未执行时不能接受审核通过，先查命令在哪里声明、Runtime 怎样提供证据、消费者在哪里核对，再确定修改位置并安排缺失证据的反例。例子说明推导方式，其组件不成为其他变更的固定要求。

复杂任务可以按可独立验证的结果分批，前置来自实际依赖，不要求未来整合先完成。被否定方案不留在最终命名和注释中。完成后对照 Software Delivery 第 4.2 节的五类内容，检查具体类、参数和失败处理是否达到本批所需精度。计划正文与运行进度分开，更新进度不能静默改变已审计划。

### 5.2 设计 schema 字段与参数取值

计划新增或修改 schema 字段、枚举、状态、分类、配置参数、接口参数或说明性文本字段时，先形成字段表，
再写实现步骤。字段会被长期读取和分支，定义含糊的代价要到下游才显现，因此在计划阶段逐项定下。

| 列 | 写什么 |
| --- | --- |
| 字段 | 实际名称；时间字段按 Timestamp 合同写成时间角色加存储后缀 |
| 回答的问题 | 这个字段回答的唯一问题 |
| 取值与含义 | 封闭取值逐个配一句说明；文本字段写明写什么、不写什么 |
| 产生方 | 谁产生或维护这个值 |
| 后续处理 | 确定性字段写出读取它的代码位置和每个取值对应的分支；说明文字写出 Agent 读后要做的动作 |
| 验证 | 覆盖每个取值或每类说明文字的测试或检查 |

设计时满足以下要求：

1. **一个字段只回答一个问题。** 不同尺度、不同产生方的事实拆成独立字段，不合成综合状态或原因码。
   例如数据最新观测的日期、最近一次写入的时间、下一次计划更新的时间、下一次更新后应到达的日期，
   是四个字段。
2. **每个字段和取值都有后续处理。** 程序据以分支的每个取值都对应代码中的明确处理和测试；说明文字
   写明 Agent 读后要做什么。说不出后续处理的字段或取值不加入。
3. **能由检查判定的异常，用检查结果表达。** 超出约定时间、与理论预期不符等情况，作为对应检查的
   失败结果报告，不另设分类。数据是否存在与是否通过检查分开表达，未通过检查的数据仍按实际存在计数。
4. **名字读出来就是意思。** 状态和结果类取值写成“主语加发生了什么”；名词类别用该类别的通用名称，
   例如日志级别写 warning、error。同一组取值使用同一构词；新设计的取值不用 gap、end、flag 这类要靠
   语境才懂的词；意思相近、容易混淆的取值改名拉开。
5. **确定性字段与说明文字分开。** 程序要判断的事实使用封闭取值；写给 Agent 或人读的说明使用文本
   字段，不写会变化的运行事实，不重复结构化字段已表达的内容，也不写待办。
6. **取值集合只定义一次。** 共同的字段和取值由所属 Design 或共享代码 schema 定义；采用共享 schema
   的项目只填写取值内容并映射到自己的存储，不再定义第二份集合。新增取值时一并提交处理方式和测试。

无声违反的样子：字段表里有取值找不到对应分支或测试；一个枚举里同时出现时间、来源状态和检查结果；
多个对象共用同一段模板说明；某个取值必须附带额外解释才能被理解。出现这些情况时回到本节重排字段，
再继续写实现步骤。

### 5.3 Author Self-Check

<!-- embedded-resource:t0:skill_author_self_check:start -->
调用外部 Reviewer 前，author 必须直接消费本 Skill 声明的、由 subject authority 拥有的 canonical checklist，不能手抄第二份 checklist。每次调用只形成临时结果表：

| `check_id` | `exact evidence` | `local result` | `unresolved finding` |
| --- | --- | --- | --- |

每个 required `check_id` 恰好出现一次，并绑定当前 exact candidate 的证据。依据本次授权目标、适用计划步骤、完成条件与排除项判断当前必要性；历史 `prior_findings` 在当前候选上重新核对，不能继承旧 verdict。经核对成立且影响本步完成的必修问题列为 unresolved finding，先在本 Skill 内修订；note 不列入该栏，也不自动实施。对证据错误或越界的历史意见，在 exact evidence 中说明理由并交回独立 Reviewer 重判，不能自行改写原结论。只有没有已知未解决的必修问题时，才冻结候选并调用独立 Reviewer。

Author Self-Check 只防止作者把自己已经看见的缺口交给 Reviewer。它不产生 `passed`、approval、admission 或任何可替代独立审核的结果，也不创建持久化 record、Registry 或跨系统 schema。
<!-- embedded-resource:t0:skill_author_self_check:end -->

使用下方 Software Delivery checklist 的计划判断，check_id 为已有序号 1 至 9。代码核对覆盖和当前内容，作者填写实际证据，不把实现阶段的未来代码或测试结果要求为计划阶段的产物。

用 engineering-change-review 指出的审核入口，传入 `--check-only --self-check-template NEW_PATH` 生成临时表。代码填写 `candidate_sha256` 和 `check_id`，作者填写 `exact_evidence`、`local_result` 和 `unresolved_finding`，完成后通过 `--self-check` 提供。自检表只保存本次证据，不登记为新的产物类别。

<!-- embedded-resource:t0:engineering_change_review_checklist:start -->
`engineering_change_reviewer` 在一次审核中完整判断以下结果：

1. 使用代码已校验的真实受审对象和证据：计划审核针对完整 CodeDesignBasis，实施审核针对 exact commit 及其已外审计划；目标和范围明确，背景未变成额外 subject；另有 SystemChangePlan 时核对相关步骤、完成条件、排除项和后续边界，不把其缺失当作统一前置失败；
2. 实现依据足以说明预期结果与职责边界；缺少应由上游决定的 Design meaning 时返回对应负责人，不从代码反推新需求，也不重新审查未改变的有效设计；真实依赖缺失、规则冲突、新证据或原处理失败使既定方案不能成立时，说明影响并交原负责人重新判断，不自行扩展范围；涉及时间或机器引用含义时使用对应 T0 的适用规则；
3. 计划的方案、范围、依赖、顺序和本次结果完整一致；审实现时再确认代码实现了这些要求。分批交付不把明确留给后续且不影响本批的结果变成当前要求，也不接受未授权副作用；本次修改造成的实际回归即使计划未逐字列出，仍属于需报告的缺陷；
4. 计划说明需要变化的输入、输出、影响和失败处理；审实现时确认实际代码与计划及所属接口一致。已有错误合同被正确消费，不为无需要的路径要求新编号或机制；
5. 计划清楚区分最终方案与必要的取舍讨论；审实现时确认代码、测试和交付文档不保留只为解释已否定方案而留下的命名、包装或兼容路径，真实兼容义务仍得到保留；
6. 计划把新行为安排到正确的既有负责人和代码位置，必要的新抽象有职责依据；审实现时确认它未增加未声明的平行实现或隐藏依赖；
7. 计划的测试与验证安排足以证明声明结果，覆盖适用的行为、负例、兼容与恢复，不要求先运行尚未实现的代码。审实现时核对实际测试证据，区分本次缺陷、既有问题和环境缺口，不把局部通过说成整体通过，也不豁免真实失败；
8. 语义判断成立后检查本次修改中供人阅读的文档、注释、错误信息与发布说明，保持事实、职责、因果、不确定性和停止条件；不把代码风格偏好当作表达缺陷；
9. 整体结论、检查结果、findings 和下一步相符；每个必须修改的问题有具体证据、适用要求、当前后果及本批处理的必要性，可选建议和未来收益不成为通过条件。

### 5.4 组织外审并交出计划

使用 engineering-change-review 组织同一个独立 engineering_change_reviewer 的计划审核。提供完整计划、授权目标、必要 Design/code context、验收要求、历史意见和已完成的 Author Self-Check。工具检查准确计划、检查项覆盖、引用和未解决问题，不要求未来 commit。

配置或工具缺失时，将实际错误和已有材料交给执行环境负责人，不临时重写 Reviewer。

收到有效 Reviewer 结论后，先核对意见的证据、范围、当前后果和本批必要性，再修订成立缺陷。note 默认不实施；错误或越界意见附理由交回独立重判，不能自行改写未通过结论。

真实依赖或上游决定缺失时返回其负责人，不因一条意见扩大计划。多轮沿用同一目标与完成条件，仍处理真实遗漏和回归。核对独立结果对应当前正文并为 passed 后，按第 4.3 节说明实施授权并交给实现负责人。后续代码仍接受 Software Delivery 规定的验证和审核。
