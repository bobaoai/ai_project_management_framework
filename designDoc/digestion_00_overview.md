# Digestion Layer Overview

## 1. 这层解决什么

`digestion` 是与 `ingestion`、`research` 并列的 T1 layer。它位于 canonical source read surface 之后、thesis / theme / portfolio judgment 之前。

它的目标不是再做一层摘要，而是在 Material Catalog 定义的素材边界内，把可读 source 消化成 typed、routed、可复用、可追踪的分析资产。

```text
Ingestion
  source connector / raw import
  -> archive object
  -> canonical read surface (`read_content.md`)

Digestion
  `read_content.md`
  -> Source Packet / Evidence Packet
  -> Expert Factory / Expert Registry
  -> Domain Route / Expertise Application
  -> Source Card (Material Catalog object; generated by selected expert)
  -> Typed Claim (Material Catalog bridge object; guarded by expert firewall)
  -> Domain Framework / Channel Routing
  -> Scenario input / provisional Scenario Prediction
  -> Expert Artifact (Material Catalog object; generated by selected expert)

Research / Analysis
  digestion-executed material objects
  -> Evidence / Thesis / Scenario / Theme / Technical Report / Portfolio Decision
```

读完本文，读者应该能够判断：

- 哪些工作属于 ingestion，哪些属于 digestion，哪些属于 research / AnalysisPlatform。
- 为什么 Fed Rate 这类专家模式应该先进入 digestion subsystem，而不是直接写 thesis。
- Digestion 负责执行哪些素材生成链路，以及这些素材如何进入 thesis / theme / portfolio decision。
- Domain Expert 如何被生产、审查、投影成 skill，以及为什么 Source Card / Typed Claim 应由对应 expert 生成。
- Independent Research Orchestrator 如何主动搜索、组装 asset source packet，并在 Source Card 生成之前选择 domain route。
- 为什么 Scenario 应该从 thesis anchor + expertise application + material evidence 生成，而不是从 raw source summary 直接生成；当前 `scenario_prediction` 只是 Digestion graph 上的 provisional execution object。
- 为什么 Digestion 需要 Postgres backend support，而不是只靠 Markdown 文件夹。
- 哪些模式可以从 Fed Knowledge Base 提炼成可复用分析框架。

结构契约入口：

- `digestion_10_structure_contract.md` 定义 Source Card、Typed Claim、Framework Card、Channel / Role Registry、Framework Route、Scenario Prediction、Expert Artifact、Promotion Link 的当前 Digestion schema、Postgres rows、文件投影、生成链路和下游消费方式；Material object 边界以 `material_00_overview.md` 及其 child contracts 为准，reusable capability 边界以 `expertise_00_overview.md` 为准。
- `digestion_11_report_package_contract.md` 定义通用 Digestion report-package contract：Expert Artifact、Source Cards、Typed Claims 如何变成 writer-ready package，以及 child contract 的 admission / inheritance 规则。
- `digestion_12_private_company_report_package_contract.md` 定义 `private_company_report_package`：继承 `digestion_11`，并补充 pricing-surface、public-comp、cannot-know、unit-of-account、blocked-output 边界。
- `digestion_20_independent_researcher.md` 定义跨资产独立研究 orchestrator、asset workspace、外部搜索 / message archive / source packet / domain route / expert handoff 的边界。
- `digestion_30_expert_factory.md` 定义 Expert Factory：如何从 reusable analytical asset 生产 domain expert、source card pattern、typed claim firewall、expert artifact schema 和 skill projection。
- `digestion_40_entity_expert.md` 定义 Entity Expert 抽象父类：什么是实体专家、与 Transmission Expert 的区别、shared structure contract（source-class taxonomy、typed-claim firewall、dossier schema、permission levels）、source cross-consumption principle。
- `digestion_41_company_expert.md` 定义 Company Expert family：company-like research target 如何在 listed-company、private-company 和未来 company child expert 之间路由，并保留共享 evidence boundary。
- `digestion_41_1_private_company_expert.md` 定义 Private Company Expert：pre-IPO / private-company source packet 如何处理 operating-company value vs instrument-specific security price、secondary-market pricing surfaces、primary-round / fund-mark evidence、public-comp calibration、`private_company_dossier` 和 cannot-know boundaries。
- `digestion_41_2_listed_company_expert.md` 定义 Listed Company Expert：public company / public equity issuer source packet 如何生成 company-owned Source Cards、CompanyTypedClaims、`single_asset_dossier`，以及如何与 `research-single-stock-analysis`、theme / thesis、portfolio decision 分层。
- `digestion_42_crypto_project_expert.md` 定义 Crypto Project Expert：crypto project source packet 如何通过 Dual-Track 分析框架（Survival/Fundamental Track + Reflexive Market Track）生成 project-level Source Cards、decision brief 和 participation status。
- `digestion_50_transmission_expert.md` 定义 Transmission Expert 抽象父类：什么是传导链专家、与 Entity Expert 的区别、shared structure contract（Transmission Chain、Channel Registry、State Map、Impact Pool、per-step evidence tier）。
- `digestion_51_ai_industry_expert.md` 定义 AI Industry Expert Family：AI 行业传导链（capex → semis → power → capacity → adoption → monetization）的 orchestration、routing 和 family-level artifact assembly。
- `digestion_51_1_ai_semiconductor_expert.md` 定义 AI Semiconductor Expert：AI 传导链 Steps 2–3 的 source digestion（semiconductor supply chain、memory cycle、chip architecture、equipment）。
- `digestion_51_2_ai_datacenter_expert.md` 定义 AI Data Center Expert：AI 传导链 Step 4 的 source digestion（power/utility、optical/networking、DC construction/cooling）。
- `digestion_51_3_ai_application_expert.md` 定义 AI Application Expert：AI 传导链 Steps 5–9 的 source digestion（enterprise adoption、monetization、demand quality）。

## 2. T1 layer 边界

### 2.1 Ingestion

`ingestion` 负责让外部材料可读、可审计、可重放。

Canonical stop point:

```text
data/research/messages/<research_id>/read_content.md
```

它不负责 source 的投资含义、claim 类型、专家框架、thesis 生命周期或 PM action。

### 2.2 Digestion

`digestion` 负责把 `read_content.md` 提升为可复用分析资产。

Material boundary:

- Material Catalog 负责定义 Source Card、Typed Claim、Expert Artifact、Evidence、Thesis、Scenario、Theme、Technical Report 等素材 contract。
- Expertise 负责定义 reusable capability：expert framework / lens、source card pattern、typed claim firewall、artifact schema、scenario prediction grammar 和 skill projection contract。
- Digestion 负责 source-understanding、domain route、framework application、generation chain、current runtime schema 和 promotion edge。
- 在 Material Catalog child contracts 投影到 runtime 之前，`digestion_10_structure_contract.md` 保留当前 object shape 的 execution detail。

核心动作：

- 独立读懂 source。
- 判断 source 可以支持什么、不能支持什么。
- 把 source 内容拆成 typed claims 或 reasoning units。
- 按 domain framework / channel / role / horizon 路由。
- 生产和维护 domain expert 的当前 Digestion projection；reusable source card pattern、claim firewall、artifact schema 和 blocked outputs 的 durable capability authority 归 Expertise。
- 在跨资产研究中先选择 domain route，再让对应 expert 生成 Source Card / Typed Claim / Expert Artifact。
- 记录 falsifier、freshness、provenance、downstream consumers。
- 组合 state、typed claims、framework routes、historical cases、falsifiers，生成 scenario prediction。
- 在 Material Catalog contract 下，产出专家 subsystem 和 research / PM workflow 可消费的中间 artifact。

Digestion 不负责最终 PM belief，也不直接授权 portfolio action。

### 2.3 Research / Analysis

`research` 和 AnalysisPlatform 消费 digestion 产物，形成更上层判断：

- `ThesisNote`
- `ThemeObject`
- `ThemeAnalyticReport`
- `SingleStockAnalysis`
- `PortfolioDecision`

Thesis 是 belief container。Digestion 是 belief 之前的 source-understanding and domain-routing layer。

边界句：

```text
digestion asset != thesis
```

Digestion 可以为 thesis 提供 typed evidence、framework、claim lineage、falsifier 和 horizon；但 thesis 的 belief、lifecycle、PM ack、position implication 仍由 research / PM workflow 管。

## 3. Reader End-State

Digestion 产物的 reader end-state 是：

- 下游 analyst 不需要重新读原文，也能恢复 source 的核心机制、边界、保留细节、排除细节、时间语义和允许用途。
- 下游 writer 能判断某个 source card / claim 可以进入哪个 expert subsystem 或 artifact。
- 下游 thesis owner 能区分 source 原始断言、digestion worker 的解释、以及 thesis 层才允许做的跨源判断。
- 下游 reviewer 能反查每条判断来自哪个 source、哪个 span、哪个 source_class、哪个 claim_type、哪个 framework edge。
- 系统能知道某个 digestion asset 是否 stale、是否被下游消费、是否被新证据 falsify。
- 系统能基于当前 digestion graph 生成条件化 scenario prediction，并说明每条路径依赖哪些 claim、channel、case 和 falsifier。

Silent violation:

```text
Source 被总结得更顺了，但下游仍必须回头读原文才能知道机制为什么成立。
```

这说明产物只是 summary，不是 digestion。

## 4. Core Objects

本节是 Digestion execution view。Canonical material contracts 已迁入 Material Catalog：

- Source Card: `material_30_source_card_contract.md`
- Typed Claim: `material_32_typed_claim_contract.md`
- Expert Artifact: `material_35_expert_artifact_contract.md`
- Evidence: `material_40_evidence_contract.md`
- Scenario: `material_80_scenario_contract.md`

### 4.1 Source Card

Source Card 是 synthesis 前的独立 source-understanding 层。

Canonical material boundary: `material_30_source_card_contract.md`。Digestion 负责 route 后生成、保存、审查和 promotion edge。

它回答：

- 这份 source 是什么。
- 它的 voice / source_class / time semantics 是什么。
- 它写了什么。
- 它没有写什么。
- 它能支持哪些 angle。
- 哪些 detail 会改变下游判断。

Source Card 不等于 writer package，也不等于 thesis note。

Source Card 也不是 generic pre-route summary。不同 domain expert 可以有不同 Source Card pattern。`Independent Research Orchestrator` 负责构建 source packet 和选择 route；对应 expert 负责生成自己的 Source Card。

### 4.2 Typed Claim

Typed Claim 是 source content 投影到 domain semantic space 后的原子判断。

Canonical bridge boundary: `material_32_typed_claim_contract.md`。Typed Claim 只有在进入 belief_delta / target_belief / promotion context 后，才成为 Evidence contract 下的 evidence input。

它至少应包含：

- `claim_id`
- `source_card_id`
- `source_ref`
- `source_class`
- `claim_type`
- `claim`
- `elaboration`
- `time_validity`
- `confidence`
- `observed_at_utc`
- `recorded_at_utc`
- `falsifiers[]`
- `source_span_refs[]`

Typed Claim 的重点不是“把话切碎”，而是防止 voice 越权。

例子：

```text
buy-side narrative 可以产 market_mapping claim；
它不能直接修改 Fed reaction function parameter state。
```

### 4.3 Framework Card

Framework Card 保存可复用的分析框架。

它回答：

- 这个框架用于解释什么问题。
- 它有哪些 state / channel / role / horizon。
- 哪类 source 可以喂它。
- 哪类 claim 可以改变它。
- 它的常见误用是什么。
- 它怎样被 falsify 或更新。

Fed Knowledge Base 的 `State Estimation -> Transmission Diagnosis -> Portfolio Expression` 就是第一批 framework candidate。

### 4.4 Channel / Role Registry

Channel / Role Registry 定义一个 domain 内的传导通道、角色生态和允许用途。

Fed Rate 例子：

- `front_end_plumbing`
- `long_end_term_premium`
- `credit_creation`
- `inflation_expectations`
- `dollar_fx`
- `asset_price_fci`
- `fed_reaction_function`
- `fiscal_treasury_supply`

每个 channel 需要定义：

- `channel_id`
- `decision_layer`
- `definition`
- `native_horizon`
- `observables[]`
- `source_roles`
- `typical_misuse[]`
- `falsifiers[]`

### 4.5 Expert Subsystem Artifact

Expert subsystem artifact 是 domain 内部的 structured read，而不是 PM-facing final report。

Canonical material boundary: `material_35_expert_artifact_contract.md`。Digestion 负责把 Source Card、Typed Claim、Framework Route 和 Scenario input 组装成当前 expert subsystem output。

Fed Rate 的第一组 artifact：

- `Regime Map`
- `Trigger Chain`
- `Stock Pool Impact`

其他 subsystem 可以有自己的 artifact，但必须保留同一条形状：

```text
source -> source card -> typed claim -> framework/channel routing -> expert artifact
```

### 4.8 Expert Factory

Expert Factory 负责生产和维护 domain experts。

它回答：

- 哪个 reusable analytical asset 足够成为 expert 或更新 expert。
- 这个 expert 的 source card pattern 是什么。
- 哪些 source_class 可以支持哪些 claim_type。
- expert 可以输出哪些 artifact，不能输出哪些 artifact。
- generated skill 如何指回 expert contract 和 version。

Expert Factory 不跑单次资产研究。单次资产研究由 `Independent Research Orchestrator` 组 source packet，再调用已存在的 expert。

### 4.9 Independent Research Orchestrator

Independent Research Orchestrator 是 Digestion 层的跨资产研究工作流 owner。

它回答：

- 研究问题和 asset identity 是什么。
- 本地 archive 是否已有足够 source。
- 是否需要外部搜索。
- 外部 source 是否已进入 message archive。
- 该 asset 研究应该 route 到哪个 expert。
- expert 输出应如何进入 dossier、decision brief、package、report draft 或 downstream promotion。

它不直接生产 generic Source Card / Typed Claim。route 之后由 expert 生产对应 digestion objects。

### 4.6 Scenario Prediction

Scenario Prediction 是 digestion graph 上的条件路径推演。

它回答：

- 当前 state 下有哪些 plausible scenarios。
- 每个 scenario 依赖哪些 typed claims、framework routes、channels 和 historical cases。
- 哪些 evidence 支持、削弱或限制这个 scenario。
- 这个 scenario 的 native horizon 是什么。
- 哪些 falsifier 或 missing confirmation 会让它降级、失效或切换路径。
- 它能进入哪个 thesis / theme / portfolio workflow，进入时应作为 evidence、background、watch trigger，还是 candidate only。

Canonical Scenario boundary: `material_80_scenario_contract.md`。当前 `scenario_prediction` 是 Digestion graph 的 provisional execution object；它可以作为 Scenario input、watch trigger 或 candidate path，但不能直接替代 thesis-anchored Scenario。

Scenario Prediction 不等于 thesis。

```text
scenario prediction = 条件路径
thesis = PM belief
portfolio decision = action / sizing / hedge implication
```

Scenario Prediction 的最低字段：

- `scenario_id`
- `subsystem_id`
- `framework_id`
- `scenario_name`
- `state_assumption`
- `path_steps[]`
- `supporting_claim_ids[]`
- `contradicting_claim_ids[]`
- `channel_route_ids[]`
- `historical_case_refs[]`
- `native_horizon`
- `likelihood_ordinal`
- `confidence`
- `falsifiers[]`
- `missing_confirmations[]`
- `allowed_use`
- `promotion_targets[]`

Silent violation:

```text
Scenario 直接从一篇 source summary 写出，没有 claim lineage、channel routing、horizon 或 falsifier。
```

这说明它是 analyst guess，不是 digestion-backed prediction。

### 4.7 Promotion Link

Promotion Link 记录 digestion asset 如何进入下游 research / analysis。

它回答：

- 哪个 thesis / theme / report 消费了这个 source card 或 claim。
- 消费时 asset 是 fresh、stale 还是 candidate。
- 下游使用的是 evidence、background、framework、falsifier，还是 rejected clue。
- 消费后是否产生了 thesis update、theme update 或 portfolio decision。

没有 Promotion Link，digestion 会变成另一个资料堆。

## 5. Fed Knowledge Base 作为第一个 dogfood

Fed Rate 适合作为 digestion 的第一条专家子系统，因为它同时具备四个压力：

1. **voice 权限差异大**：Fed primary record、quasi-official reporter、academic framework、market interpretation、buy-side narrative 都会说 Fed，但它们能支持的 claim 不一样。
2. **传导链长**：cut / hold / hike 本身不是市场结果，结果取决于 front-end、long-end、credit、dollar、expectations、FCI 等 transmission channel。
3. **时间语义敏感**：FOMC、SEP、press conference、market recap、Substack newsletter、historical case 的 horizon 不同。
4. **容易被滥用**：一个局部 plumbing calm 很容易被错误放大成 risk-on conclusion。

Fed Knowledge Base 当前提供的可复用 digestion patterns：

- Source Card prepass。
- `source_class x claim_type` firewall。
- `State Estimation -> Transmission Diagnosis -> Portfolio Expression` 决策流水线。
- Channel registry + horizon + falsifier。
- Scenario prediction as conditional path, not thesis belief。
- Expert artifact: Regime Map / Trigger Chain / Stock Pool Impact。
- prompt module split: `GENERAL_MODULE / CUSTOMIZE_MODULE / DATA_DEPENDENT_MODULE`。

Fed-specific 不应直接 promotion 的内容：

- FOMC / SEP / Powell / Timiraos 等实体。
- Framework / Parameter / Operation 的 Fed 术语本体。
- Fed-specific transmission channel 名称。
- Fed watcher source list。

Portable layer 应提炼的是：

```text
domain source -> source card -> typed claim -> channel routing -> expert artifact -> downstream thesis / PM decision
```

## 6. Postgres Backend Support

Digestion 信息量会变成图状结构。只靠 Markdown 文件夹无法可靠回答：

- 某个 claim 被哪些 thesis / theme / report 用过。
- 某个 source card 是否 stale。
- 某个 framework 是否被多个 subsystem 复用。
- 某条 falsifier 是否已经被新 evidence 触发。
- 某个 voice 是否越权产出了不该产的 claim_type。
- 哪些 digestion assets 需要重新 review。
- 当前 scenario prediction 依赖的 claim / channel / case 是否仍然 fresh。

因此 Digestion 使用 Postgres 作为 backend source of truth for registry, edges, provenance, freshness, and query.

文件系统可以保留人类可读 projection，但查询、关系、freshness、reverse refs 不依赖扫目录。

### 6.1 Postgres owns

Postgres owns:

- digestion object registry
- object identity and type
- canonical path pointer
- content hash
- source lineage
- typed edges
- source_class / claim_type route checks
- framework / channel mappings
- freshness state
- scenario prediction dependency state
- downstream consumers
- module hashes for worker prompts
- run logs and validation status

### 6.2 Filesystem owns

Filesystem owns:

- human-readable Markdown projection
- review-friendly diffs
- exported packages
- temporary draft artifacts
- artifact bodies that are easier to inspect as files during v0 dogfood

Every file-backed digestion object must have a Postgres row with `canonical_path` and `content_hash`.

Silent violation:

```text
An agent can find a Markdown source card, but Postgres has no object row or edges for it.
```

This means the object exists as a note, not as a digestion asset.

Initial filesystem projection:

```text

  source_cards/
  claims/
  frameworks/
  expert_subsystems/
    fed_rate/
      source_cards/
      claims/
      frameworks/
      channel_registry/
      scenarios/
      artifacts/
  exports/
```

This layout is a projection, not the query backend.

Rules:

1. Every durable file under `data/digestion/` must have a corresponding `digestion_objects` row.
2. Every source-derived object must link back to `data/research/messages/<research_id>/read_content.md` or another declared canonical source.
3. Every downstream use must create a `promotion_link` or typed edge.
4. Generated indexes under `data/digestion/` are derived from Postgres, not hand-maintained.

## 8A. Expert Taxonomy

Domain experts 分为两类，按分析 lens 而非按资产类别：

| 系列 | Expert 类型 | Primary Lens | 例子 |
|---|---|---|---|
| 4x | Entity Expert | 单一实体的 quality / value / risk | Company (41, 41_1, 41_2), Crypto Project (42) |
| 5x | Transmission Expert | 传导链 / 供应链的 signal propagation | Fed Rate (52, 外部 macro_fed_kb), AI Industry (51, 51_1, 51_2, 51_3) |

Abstract parent docs: `digestion_40_entity_expert.md` (4x), `digestion_50_transmission_expert.md` (5x).

**同一条 source 可以被多个 expert 消费。** Entity Expert 和 Transmission Expert 从各自 lens 生成独立的 Source Card 和 Typed Claims。

区分原则：
- 如果 expert 的核心问题是 "这个实体值多少 / 活不活得下来 / quality 怎么样" → Entity Expert
- 如果 expert 的核心问题是 "一个 signal 如何从 A 传导到 B 再到 C" → Transmission Expert

## 9. Subsystem Admission

Not every theme deserves a digestion subsystem.

Create a digestion expert subsystem only when:

- source volume is high,
- source voice authority differs materially,
- claims need typed routing before synthesis,
- transmission or mechanism chains are multi-step,
- the domain repeatedly affects PM / portfolio judgment,
- stale or misrouted evidence can materially distort decisions.

Good candidates:

- Fed Rate / monetary transmission
- oil / Hormuz / energy shock
- AI capex / semis / data-center power
- consumer demand sensing
- liquidity / plumbing
- crypto project analysis

Poor candidates:

- one-off articles,
- narrow learning notes,
- themes that only need a thesis note,
- sources whose claim authority is uniform and low-risk.

## 10. Interface With Existing Layers

### 10.1 Ingestion interface

Input:

```text
data/research/messages/<research_id>/read_content.md
```

Digestion should not read archive internals unless `read_content.md` exposes an audit path and the specific worker task requires audit.

### 10.2 Research interface

Research consumes digestion via:

- source card refs,
- typed claim refs,
- framework refs,
- promotion links,
- freshness / falsifier state.

Research should not silently re-read raw source to recover reasoning that a digestion artifact failed to preserve.

### 10.3 AnalysisPlatform interface

AnalysisPlatform consumes only promoted digestion assets or expert subsystem artifacts, not every candidate source card.

PM-facing artifacts should cite:

- thesis refs,
- theme refs,
- digestion claim refs where source-level reasoning matters,
- expert artifact refs where domain subsystem judgment matters.

## 11. First Implementation Slice

First dogfood should stay narrow:

1. Add Postgres tables for `digestion_objects`, `digestion_edges`, `digestion_prompt_runs`.
2. Register Fed Rate as first `subsystem_id = fed_rate`.
3. Import or mirror a small set of Source Cards from the Fed KB dogfood.
4. Create one framework card for `State Estimation -> Transmission Diagnosis -> Portfolio Expression`.
5. Create one channel registry slice for `front_end_plumbing`.
6. Create one digestion-backed scenario prediction using typed claims, channel routes, horizon, and falsifiers.
7. Link 2-3 typed claims or one scenario prediction to one downstream thesis or theme as promotion links.

Do not start with UI.

Do not backfill all historical research.

Do not build a generic graph database abstraction before the first Fed Rate dogfood path works.

## 11A. Expert Subsystem Seeds

### Fed Rate

Fed Rate remains the first full dogfood because it has the strongest combination of voice firewall, transmission chains, time semantics, and PM relevance.

Entry design:

```text
video_parser/macro_fed_kb/design/
```

### Crypto Project Expert

Crypto Project Expert is the first non-Fed digestion seed. It starts from a framework-source PDF rather than from a complete source corpus.

Entry design:

```text
designDoc/digestion_42_crypto_project_expert.md
```

Its reusable core is `Dual-Track Crypto Project Analysis`:

```text
Evidence Permission Layer
  -> publicly observable / proxy inferable / cannot know

Survival / Fundamental Track
  -> project survival, fundamental floor, hard-data downside

Reflexive Market Track
  -> cycle heat, float, unlocks, liquidity, distribution pressure proxy

Decision Layer
  -> participation status, price bands, invalidation triggers, confidence
```

The expert is admitted because crypto project analysis has high source-type diversity, fast freshness decay, strong scenario-prediction need, and a high risk of confusing narrative heat, exchange attention, or proxy market structure with fundamental adoption.

### AI Industry Expert (Transmission)

AI Industry Expert Family 是 Digestion 层覆盖 AI 行业传导链的 expert umbrella。它做 orchestration 和 routing，下辖两个 child experts。

Entry design:

```text
designDoc/digestion_51_ai_industry_expert.md
designDoc/digestion_51_1_ai_semiconductor_expert.md
designDoc/digestion_51_2_ai_datacenter_expert.md
designDoc/digestion_51_3_ai_application_expert.md
```

Structure:

```text
AI Industry Expert (51, umbrella / orchestrator)
  -> AI Infrastructure Expert (511): capex cycle, semis supply chain, power/DC
  -> AI Application Expert (512): enterprise adoption, monetization, demand quality
```

It defines a 9-step Transmission Chain from capex decision to end-user monetization. The family-level router splits sources to the correct child expert; the umbrella assembles cross-child artifacts (State Map, Stock Pool Impact).

The expert family is admitted because AI industry analysis has high source-type diversity (practitioner curated, specialized research, company filings, industry data), multi-step transmission (capex → chips → power → capacity → pricing → adoption → revenue), and a high risk of confusing narrative heat with real demand proof.

## 12. Open Questions

1. Should file bodies remain canonical in v0 with Postgres as registry / graph, or should Postgres own canonical object body after dogfood?
2. Should `data/digestion/` live under `data/research/digestion/` during migration, or stand as a top-level T1 data root immediately?
3. Should Source Card be universal across all digestion subsystems, or should each subsystem own a compatible but specialized card schema?
4. How should stale digestion assets invalidate downstream thesis / theme packages?
5. Which existing `agent_evidence.json` or interpretation framework objects should be migrated, and which should remain legacy research artifacts?

## 13. Non-Goals

Digestion does not:

- fetch raw sources,
- replace `read_content.md`,
- write final theme reports,
- approve thesis lifecycle transitions,
- make portfolio decisions,
- provide a wiki UI as the first milestone,
- collapse all domain expertise into one generic schema.

The layer exists to make research materials reusable before they become belief.
